# Rich Value Decoding Feasibility Study

## Summary

Goal: improve `bpftrace` output generated by Sigminer so pointers and aggregates can be rendered as useful values instead of raw addresses where DWARF information makes that possible.

The implementation was intentionally done as a feasibility study rather than a full production-hardening pass:

- preserve the existing shallow type/signature path for speed and simplicity
- add a separate rich type/signature path for richer script generation
- keep current callers working unless they explicitly opt into the rich path
- validate the approach with mock symbols and script-generation tests

## 1. Dual-Mode Type Metadata

### Plan

Keep the existing cutdown `TypeEntry` model for fast lookups and introduce a separate recursive rich model for:

- pointee metadata
- aggregate members
- arrays
- parameter names
- string-like classification

### Implemented

Added parallel rich model types in:

- `include/sigminer/signature.h`
- `include/sigminer/sigminer_c.h`

New rich types:

- `RichTypeEntry`
- `RichTypeMember`
- `RichParameter`
- `RichSignature`
- `RichResult`

The existing shallow types remain intact and continue to back the old APIs.

## 2. Rich Signature Extraction

### Plan

Add a dedicated rich-signature extraction API rather than making the existing shallow extraction path recursively walk all DWARF data.

### Implemented

Added rich extraction APIs in:

- `include/sigminer/sigminer.h`
- `include/sigminer/sigminer_c.h`
- `src/sigminer.cpp`
- `src/sigminer_c.cpp`

New public entry points:

- `GetRichSignatureFromSharedObjectBySymbol(...)`
- `SIGMINER_GetRichSignatureFromSharedObjectBySymbol(...)`

Rich extraction logic was implemented in:

- `src/signature_builder.cpp`

Current extraction behavior:

- resolves pointee types recursively
- resolves struct/class/union members recursively
- captures fixed array counts where discoverable
- captures parameter names from `DW_TAG_formal_parameter`
- marks string-like types for `char*` and `char[N]`
- stops recursive expansion using depth and active-DIE guards

## 3. Rich bpftrace Rendering

### Plan

Keep the existing shallow mapper path and add a second rich rendering path that emits typed `bpftrace` code for:

- strings
- pointer-to-primitive dereference
- pointer-to-aggregate expansion
- aggregate member printing
- array rendering with limits

### Implemented

Extended:

- `src/internal/bpftrace_mapper.h`
- `src/bpftrace_mapper.cpp`

Added rich rendering controls to `BpftraceRenderOptions`:

- `EnableRichTypePrinting`
- `MaxAggregateDepth`
- `MaxAggregateMembers`
- `MaxArrayElements`

Added a dedicated rich script builder:

- `BuildRichBpftraceUprobeScript(...)`
- `SIGMINER_BuildRichBpftraceUprobeScriptForTarget(...)`

Current rich rendering behavior:

- `char *` and `const char *` use `str(uptr(...))`
- pointer-to-primitive prints address and dereferenced typed value
- pointer-to-aggregate prints address and recursively expanded members
- aggregate-by-value arguments can be expanded when represented in the probe
- arrays are handled in a limited way, with special treatment for string-like arrays
- unsupported or depth-limited values fall back to labeled messages rather than failing silently

Compatibility fixes made during feasibility testing:

- use C-compatible type spellings in generated aggregate preambles
- use unique scratch variables per rendered field to satisfy `bpftrace` typing rules
- avoid raw pointer truthiness in `if (...)` and use explicit `!= 0`

## 4. Generated Type Preambles

### Plan

Emit only the aggregate types required by the rendered rich values, in a form `bpftrace` can parse.

### Implemented

The rich mapper now emits aggregate preamble definitions before the probe blocks.

Behavior:

- referenced aggregate types are collected recursively
- definitions are emitted once per type
- unnamed types are sanitized into deterministic names
- emitted declarations are minimal and aimed at field access compatibility

This is intentionally not a full source-level C/C++ reconstruction.

## 5. ABI and Ownership

### Plan

Minimize disruption by adding rich structs and APIs rather than inflating the shallow ABI.

### Implemented

The shallow ABI was preserved and a parallel rich ABI was added.

Implemented in:

- `include/sigminer/sigminer_c.h`
- `src/sigminer_c.cpp`

Added:

- rich C struct conversion
- rich allocation/copy paths
- rich free paths
- `SIGMINER_FreeCString(...)` implementation

## 6. Mock Coverage and Validation

### Plan

Validate feasibility with mock symbols that exercise:

- string pointers
- primitive pointers
- aggregate pointers

### Implemented

Mock symbols added in:

- `test/mock_lib.c`

Symbols:

- `DerefInt`
- `CountString`
- `SumTraceNode`

Live workload updated in:

- `test/mock_live.cpp`

The loop now calls all three functions continuously so they can be traced live with:

- `./build/bpftrace <pid> CountString ./build/libmock_lib.so`
- `./build/bpftrace <pid> DerefInt ./build/libmock_lib.so`
- `./build/bpftrace <pid> SumTraceNode ./build/libmock_lib.so`

Automated script-generation regression test added in:

Build integration added in:

- `CMakeLists.txt`

## 7. What Was Left Intentionally Incomplete

This feasibility-study branch does not fully implement every item from the original plan.

Known incomplete areas:

- aggregate return-by-value rich decoding is not implemented
- array rendering exists but is not broadly exercised or hardened
- no rich bulk-resolved-symbol builder was added alongside the shallow bulk builder
- no large-scale union/typedef-heavy/nested-array compatibility matrix was added
- no end-to-end automated runtime validation against multiple `bpftrace` versions was added
- fallback behavior is practical but not yet polished into a stable product surface

## 8. Outcome

The branch demonstrates that Sigminer can be extended to generate richer `bpftrace` scripts using a parallel rich DWARF path without sacrificing the existing shallow path.

Feasibility demonstrated:

- rich type extraction from DWARF
- opt-in richer script generation
- working live decoding for:
  - string pointers
  - primitive pointers
  - aggregate pointers

The branch should be treated as a working exploration and base for hardening, not as the final design endpoint.
